## 2. Хостинг до окончательного выбора
Сравнить три варианта: Timeweb Cloud, Supabase, Helios.
Timeweb — кандидат на отечественный вариант; бесплатность Supabase и/или факультетского доступа подтвердить текущими условиями.
По каждому записать: дату, официальный источник, СУБД/версию, постоянный free или временный trial/грант, цену,
лимит хранения, число подключений, IPv4/IPv6/TLS, сетевые ограничения, собственный результат подключения,
возможность отдельного пользователя преподавателя с SELECT/INSERT/UPDATE/DELETE только tasks.
Не называть просмотр сайта проверкой SQL-доступа. Недоступность фиксировать с точной ошибкой без секретов.
Для Helios проверить SSH-доступ, psql, доступную БД, квоты/ограничения, право создания роли или согласованный туннель.
Не передавать основной SSH/ИСУ/Moodle-пароль. Если отдельный доступ невозможен — выбрать иную площадку или согласовать способ доступа.

## 3. Интеграционная приёмка API
- GET /login/ без токена: 200 text/plain, точный логин.
- Все /api/: неправильный/отсутствующий токен 401, ошибка JSON.
- GET /api/author/: точные login/fullName.
- POST /api/tasks/: 201; id UUID; серверные ownerLogin/createdAt/done=false.
- GET /api/tasks/?runId=...: 200 массив только автора/запуска; пустой [].
- GET/PATCH/DELETE по id: 200/200/204; отсутствие 404; неверный UUID 400.
- title: trim, пустая строка/пробелы/201 символ/не строка — 400.
- runId: нет/пустой/65 символов/пробелы/неверные символы/не строка/повторный query — 400.
- done: только true/false; строки, null и числа — 400.
- POST лишнее поле; PATCH пустой/лишние поля; malformed JSON; массив/null вместо объекта — 400.
- DELETE 204 без тела. Все ответы API с телом application/json.
- Недоступная БД: 503. Данные после рестарта сохранены.
- Проверить завершающий / на всех обязательных маршрутах.

## 4. Независимый доступ к БД
Создать отдельные LOGIN-роли приложения и преподавателя без SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS.
Выдать CONNECT к учебной БД, USAGE к схеме и SELECT/INSERT/UPDATE/DELETE только tasks.
Не давать роль владельца таблицы, ALL ON ALL TABLES или административные ключи.
Проверить права реальным подключением под каждой ролью; проверить отсутствие доступа к чужим данным/DDL.
Учитывать унаследованные роли и PUBLIC-привилегии; одних GRANT недостаточно для доказательства изоляции.
Если таблица не в отдельной учебной БД, проверить доступ к другим объектам особенно внимательно.
Сетевая доступность должна быть подтверждена с машины преподавателя/через согласованный туннель.

## 5. Проверка в обе стороны
- API INSERT → SELECT напрямую из БД.
- API PATCH → SELECT напрямую из БД.
- SQL UPDATE → GET по id и список; кнопка «Обновить» в UI.
- SQL INSERT → GET списка с тем же owner_login и run_id.
- API DELETE → SELECT не находит запись.
- SQL DELETE → API 404 и отсутствие в списке.
Использовать отдельный runId для тестов, не удалять персональное manual-дело.
